# ADR-001 도구 스키마 설계: 작게, 검증하고, 에러로 가르친다

날짜: 2026-10-27 · 상태: 채택

## 문제
LLM 이 도구를 잘못 부르는 방식은 세 가지다. (1) 없는 도구 호출, (2) 인자 형식 오류, (3) 맞는 형식이지만 위험한 내용(예: `run_sql` 에 UPDATE).
"LLM 이 올바르게 호출할 수 있는 API" 를 만드는 것이 공고들이 공통으로 요구하는 역량이다.

## 결정
1. **인자는 pydantic 모델로 선언**하고 스키마(JSON Schema)를 자동 생성한다. `title` 필드는 제거해 소형 모델이 덜 헷갈리게 한다.
2. **검증 실패는 모델에게 되돌려준다.** "인자 검증 실패. limit: Input should be less than or equal to 500. 스키마에 맞게 고쳐 다시 호출하세요" 처럼 다음 행동이 보이는 문장으로.
3. **범용 도구 1개 + 자주 쓰는 안전한 전용 도구**: `run_sql` 하나로 모든 질문을 풀 수 있지만, `get_order`, `get_customer` 처럼 자주 쓰는 조회는 조인·마스킹·지연일수 계산까지 끝낸 전용 도구로 둔다. 소형 모델의 SQL 실수를 줄이고 토큰도 절약한다.
4. **`run_sql` 은 이중 방어**: 문자열 가드(SELECT/WITH 단일 문장, 금지 키워드, LIMIT 강제) + SQLite 읽기 전용 연결과 authorizer. 가드를 우회해도 DB 가 거부한다(테스트 `test_readonly_connection_rejects_writes_even_without_guard`).
5. **설명(description)에 "언제 쓰는지" 를 적는다.** "규칙 질문에 반드시 쓴다", "SQL 전에 컬럼명을 확인한다" 처럼. 모델이 도구 선택을 설명문에 의존하기 때문이다.

## 대안과 기각 이유
- 도구를 테이블별 CRUD 로 수십 개 만들기: 스키마가 커져 프롬프트 토큰이 늘고 소형 모델 선택 정확도가 떨어진다.
- `run_sql` 없이 전용 도구만: 예상 못 한 질문(집계·조인)을 못 푼다.

## 결과
단위 테스트 7개(가드)·3개(도구). 실전에서 14B 모델이 `limit` 을 1 로 보내는 등 스키마 범위 안에서만 움직였다.
