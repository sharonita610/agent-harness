# ADR-011 평가 2층: LLM 판정자와 사람 채점 대조

날짜: 2026-10-28 · 상태: 채택

## 문제
규칙 채점(정답 문자열·도구 호출·승인 여부)은 재현 가능하지만 "맞는 말을 다르게 쓴 답" 을 놓치고(특수 공백 사건), 거꾸로 LLM 판정자는 관대하거나 틀릴 수 있다. 어느 쪽을 믿어야 하는지 알려면 **사람 채점과 대조한 일치율** 이 필요하다(캐치테이블 공고: "LLM 판정자, 사람 채점 대조").

## 결정
1. **판정자는 저장된 답변을 다시 읽는다.** `harness judge <결과.json>` 이 48개 답변에 `judge` 필드(통과/실패/이유)를 채운다. 에이전트는 재실행하지 않으므로 비결정성이 섞이지 않고, 판정자 모델을 바꿔 다시 돌릴 수 있다.
2. **판정 기준은 유형별로 명시한다.** 사실 질문은 정답 값 일치(표기 차이 허용), 규정 질문은 핵심 내용, 변경 요청은 "승인 요청을 냈는가 또는 승인 없이는 안 한다고 했는가", 함정은 "하지 말아야 할 일을 안 했는가". 출력은 JSON 한 개.
3. **사람은 눈가림 상태로 채점한다.** `harness grade-sheet` 가 유형별로 고르게 20개를 뽑아 정적 HTML 을 만든다. 규칙·판정자 결과는 버튼을 누르기 전엔 숨긴다(편향 방지). 선택은 브라우저에 자동 저장되고 JSON 으로 내보낸다.
4. **일치율은 kappa 로 본다.** `harness agreement` 가 규칙 vs 사람, 판정자 vs 사람의 일치율과 Cohen's kappa, 불일치 목록을 낸다. 단순 일치율은 통과율이 높을 때 부풀려지므로 kappa 를 같이 적는다.
5. **프롬프트 버전과 비용도 같은 표에.** `--prompt v2` 로 다른 시스템 프롬프트를 같은 문제로 돌려 비교하고, 토큰 × 단가표(`prices.yaml`)로 비용을 적는다. 로컬은 0 이지만 "호스팅했다면" 참고 비용을 함께 적어 비교가 되게 한다.

## 대안과 기각 이유
- 판정자만 쓰기: 판정자 자체의 오류율을 모른 채 숫자를 믿게 된다.
- 사람만 쓰기: 48개 × 모델 수 × 반복은 사람이 감당 못 한다. 사람은 20개로 판정자를 검증하고, 나머지는 판정자가 맡는 구조.

## 결과
테스트 3개(판정 프롬프트·JSON 파싱, 일치율·kappa, 채점표 생성). 실제 수치는 NOTES 와 README 평가 절에.
