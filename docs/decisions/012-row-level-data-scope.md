# ADR-012 사용자별 데이터 범위: 프롬프트가 아니라 데이터 층에서

날짜: 2026-10-28 · 상태: 채택

## 문제
역할(ADR-010)은 "무엇을 할 수 있는가" 를 가른다. "무엇을 볼 수 있는가" 는 별개다. 영업 담당자는 자기 지역 거래처만, 본사 운영팀은 전체를 봐야 한다. 시스템 프롬프트에 "부산만 봐" 라고 쓰는 방식은 모델이 틀리거나 지시문 주입에 무너지면 그대로 샌다.

## 결정
1. **범위는 연결에 씌운다.** 사용자의 `scope`(`region` / `customer_ids`)로 거래처를 고르고, 주문·주문상품·배송·메모·상태이력을 그 거래처의 것으로 거르는 **임시 뷰를 같은 이름으로** 만든다. SQLite 는 이름이 겹치면 temp 스키마를 먼저 찾으므로, 모델이 어떤 SELECT 를 쓰든 범위 밖 행은 존재하지 않는다. 상품·재고·창고·규정 문서는 공통이라 거르지 않는다.
2. **우회 경로를 막는다.** 범위 사용자의 `run_sql` 은 `main.` / `temp.` 스키마 명시를 거부한다. 뷰 정의에 들어가는 값은 정수와 안전한 문자열만 허용한다.
3. **쓰기 도구도 같은 연결로 확인한다.** 상태 변경·메모·삭제는 실행 전에 범위 연결에서 주문이 보이는지 확인하고, 안 보이면 "조회 범위 밖" 으로 거절한다.
4. **프롬프트는 안내만.** "이 사용자는 부산 지역 거래처만 볼 수 있다" 는 문장을 붙여 모델이 '없음' 을 자연스럽게 설명하게 하되, 강제는 1~3 이 한다.
5. **서비스는 범위별 레지스트리를 캐시**한다. 문서 색인은 공유하고 DB 연결만 범위별로 만든다.

## 대안과 기각 이유
- 프롬프트 지시: 강제력 없음(위 문제).
- 쿼리 재작성(WHERE 자동 삽입): 조인·서브쿼리·CTE 를 전부 다루려면 SQL 파서가 필요하고 구멍이 생긴다. 뷰는 엔진이 보장한다.
- 테이블 복제(범위별 DB): 데이터 동기화 문제.

## 결과
테스트 3개(파싱·주입 방지, 범위 테이블 전부·조인·우회·쓰기 차단, 서비스 사용자별). 실제 모델: 같은 질문이 전체 255건 → 부산 담당자 39건, 범위 밖 주문 조회는 "존재하지 않습니다".
