# ADR-017 멀티에이전트: 팩 비서들을 A2A 로 잇고 총괄 비서가 위임한다

날짜: 2026-10-29 · 상태: 채택

## 문제
공고는 "멀티에이전트 프레임워크와 MCP·A2A 같은 에이전트 프로토콜 활용 경험" 을 묻는다. 우리에겐 성격이 다른 비서 세 개(회사 데이터·회로 시뮬레이션·공정 NG)가 각각 서비스로 떠 있다. 이들을 한 질문에서 함께 쓰려면 비서끼리 부르는 표준 방식이 필요하고, 그게 A2A(Agent-to-Agent) 프로토콜이 하는 일이다. MCP 가 "에이전트 ↔ 도구" 라면 A2A 는 "에이전트 ↔ 에이전트" 다.

## 결정
1. **각 팩 서비스가 A2A 에이전트가 된다.** `/.well-known/agent-card.json`(이름·설명·스킬·능력·인증 방식)과 JSON-RPC `/a2a`(`message/send`, `message/stream`, `tasks/get`, `tasks/cancel`). 새 실행 엔진을 만들지 않고 **기존 잡 큐·저장소·결재 브로커 위에 프로토콜 면만 얹었다**: 태스크 = 실행(run), contextId = 세션, 아티팩트 = 답변 텍스트 + 도구가 만든 그림(file 파트). 상태 매핑은 queued→submitted, running→working, done→completed, failed→failed, cancelled→canceled.
2. **사람 결재는 A2A 로 넘기지 않는다.** 하위 비서가 write 도구의 결재를 기다리면 태스크는 `input-required` 가 되고, 상태 메시지에 "어느 도구, 어떤 인자, 어디서 결재하나" 가 적힌다. 결재는 그 비서의 화면에서 사람이 한다. 상위 에이전트는 결재 대기를 보고하고 완료됐다고 말하지 않는다(평가 r06). 권한의 경계를 프로토콜 경계와 맞춘 것이다.
3. **총괄 비서는 네 번째 팩이다.** 도구는 A2A 클라이언트 세 개뿐(`list_agents`·`delegate`·`check_task`). 같은 루프·트레이스·평가를 그대로 쓰므로 "멀티에이전트" 가 별도 프레임워크가 아니라 **같은 플랫폼의 팩 하나** 로 들어온다. 위임 대상은 Agent Card 의 별칭(`metadata.aliases`, 회사/회로/공정)으로 고른다.
4. **blocking 전송.** `message/send` 에 `configuration.blocking` 을 주면 하위 실행이 끝나거나 결재 대기에 들어갈 때까지 기다렸다가 태스크를 돌려준다. 총괄 비서는 한 스텝에서 비서 둘을 순서대로 부르고 답을 합친다.

## 결과
- 복합 질문("지연 주문 몇 건 + RC 차단 주파수") 을 총괄 비서가 회사 비서와 회로 비서에 나눠 보내고 합쳤다: 4스텝 29초, 출처 표기.
- 평가 8문제(라우팅 3·복합 1·규정 1·결재 대기 1·거절 전달 1·되물음 1)는 README 표.
- 잡 큐의 잠복 결함을 찾았다: 스레드풀에서 `asyncio.Queue.put_nowait` 를 호출해 워커가 깨어나지 않을 수 있었다(기존 `/jobs` 는 다른 요청이 루프를 깨워 우연히 동작). `call_soon_threadsafe` 로 고치고 A2A blocking 테스트가 이를 고정한다.

## 대안과 기각 이유
- 총괄 비서가 하위 비서의 도구를 직접 다 갖기(단일 에이전트): 도구 41개를 한 프롬프트에 넣으면 소형 모델이 고르지 못하고, 팩별 권한·범위·결재가 섞인다. 경계를 서비스로 두는 편이 운영에도 맞다.
- LangGraph/CrewAI 로 오케스트레이션: 프레임워크가 주는 건 그래프 상태·체크포인트·스트리밍인데, 우리는 이미 저장소·SSE·트레이스가 있다. 같은 루프를 LangGraph 로 한 번 더 짜서 비교한 기록은 `docs/experiments/langgraph/`(별도 실험).
- 푸시 알림(pushNotifications): 결재 완료를 상위에게 알리는 데 유용하지만 범위를 넘는다. `check_task` 폴링으로 대신한다.

## 한계
A2A 의 인증은 API 키 헤더만 지원한다. 스트리밍은 저장된 이벤트를 0.4초 간격으로 폴링해 만든다. 총괄 비서는 하위 비서의 되물음을 그대로 전달할 뿐 대화를 이어 주지 않는다(contextId 는 유지하므로 다음 질문에 이어 보낼 수는 있다).
