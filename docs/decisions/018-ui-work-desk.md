# ADR-018 화면을 "채팅 타임라인" 에서 "업무 데스크" 로 바꾼다

날짜: 2026-10-29 · 상태: 채택

## 문제
첫 화면은 채팅창 하나에 이벤트 타임라인이 쌓이는 구조였다. 개발자가 루프를 지켜보기엔 좋았지만, 실무자(공정 엔지니어·회로 설계자·운영 담당)가 쓴다고 보면 세 가지가 걸렸다.
1. **결과가 JSON 원문이다.** 도구가 돌려준 표·측정값·출처가 `{"columns": ...}` 그대로 보여서 답을 믿으려면 원문을 읽어야 했다.
2. **비서가 네 개인데 화면이 네 개다.** 총괄 비서가 하위 비서에게 위임하면 그 비서의 결재는 다른 포트의 화면에 가서 해야 했다. 결재자가 창 네 개를 띄워야 한다.
3. **"AI 제품" 티가 난다.** 말풍선·스트리밍 커서·이벤트 나열은 챗봇 데모의 문법이고, 업무 도구의 문법이 아니다.

## 결정
1. **한 장의 작업지.** 질문 하나가 카드 한 장이 되고 순서는 질문 → 답 → 근거 카드 → (접힌) 확인 과정이다. 근거 카드는 도구 결과의 **모양** 으로 그린다: `{columns, rows}` 나 평평한 행 목록은 표, `measurements` 는 큰 숫자, `source` 가 있는 목록은 출처, 위임 결과는 인용, 그림 URL 은 그림, 나머지는 키·값, 그래도 안 되면 접힌 JSON. 팩마다 렌더러를 쓰지 않고 모양 규칙 하나로 네 팩을 다 덮는다(`ui/src/components/ResultCard.tsx`). 둘러보기 도구(`list_*`, `describe_table`)는 근거에서 빼고 확인 과정에만 남긴다.
2. **비서 전환은 사이드바, 결재는 한 결재함.** 서비스에 `GET /workspace`(HARNESS_WORKSPACE 의 비서들 agent card)와 CORS 를 더해, 총괄 비서 화면 하나에서 하위 비서 세 개로 전환하고(`api.ts` 의 base URL 교체) 결재함은 모든 비서의 `/approvals?status=pending` 을 모아 보여 준다. 전표에는 어느 비서의 요청인지 적힌다. 결재 버튼은 해당 비서 서비스로 간다. 작업지는 비서별로 따로 쌓이고, 한 비서가 결재를 기다려도 다른 비서에게 물을 수 있다.
3. **실행 상세는 드로어.** 트레이스·이벤트 원문은 작업지의 "실행 상세" 로만 열리는 오른쪽 드로어로 보낸다. 답이 끝나도 자동으로 열지 않는다.
4. **서버는 결과 원본을 이벤트에 싣는다.** `tool_result` 이벤트가 4,000자 이하면 `result` 에 구조 그대로 담는다(이전엔 300자 미리보기 문자열뿐). 저장된 실행에서도 같은 카드를 다시 그린다.
5. **디자인.** 차분한 회색 종이와 먹, 강조색은 청록 하나, 도장 빨강은 결재 전표에만. 그림자·말풍선 없음, 14px 기준, 글꼴 Pretendard 하나. 유일하게 힘을 준 요소는 결재 도장이다. 밝게·어둡게·자동 전환은 사이드바에서.

## 결과
- 같은 질문의 답이 표·숫자·출처 카드로 보이고 JSON 은 "원문 보기" 뒤로 들어갔다. 공정 비서의 급증 탐지 결과는 표 한 장, 회로 비서의 측정값은 큰 숫자 + 그래프, 총괄 비서의 위임 답은 인용으로 보인다.
- 결재자는 총괄 비서 화면 하나만 열어 두면 된다. 공정 비서가 티켓 결재를 요청하면 사이드바의 그 비서에 빨간 숫자가 뜨고 결재함에 전표가 온다. 승인하면 도장이 찍히고 그 비서의 작업지 전표에도 같은 도장이 찍힌다.
- 캡처는 `scripts/capture_ui.py` 가 헤드리스 Chrome 으로 실제 실행을 돌려 찍는다. README 의 화면은 전부 이 스크립트 산출물이다.

## 대안과 기각 이유
- **팩별 전용 화면.** 결과를 가장 잘 보여 줄 수는 있지만 팩을 추가할 때마다 화면 코드를 쓰게 되어 "팩 폴더 하나로 도메인 교체" 가 깨진다. 모양 규칙 + 팩이 주는 라벨로 충분했다.
- **결재를 A2A 로 상위 비서에 넘기기.** ADR-017 의 결정(권한 경계 = 프로토콜 경계)을 유지한다. 화면이 여러 서비스를 직접 부르는 쪽이 단순하고 감사 기록도 각 서비스에 남는다.
- **상태 관리 라이브러리·컴포넌트 킷 도입.** 화면이 작아 필요 없고, 의존성이 늘면 심사하는 쪽이 읽기 어렵다.

## 한계
- 결재함은 3초 폴링이다. SSE 로 바꾸면 즉시 뜨지만 서비스 네 개의 스트림을 한 화면에서 관리해야 해서 뒤로 미뤘다.
- 작업지는 새로 고치면 사라진다(실행 기록에는 남는다). 작업지를 기록에서 다시 여는 기능은 다음 차례.
- 로그인 키 하나를 네 서비스에 같이 쓴다. 서비스마다 사용자 파일이 다르면 결재함이 일부만 보인다.
