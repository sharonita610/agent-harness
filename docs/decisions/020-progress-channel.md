# ADR-020 긴 도구의 진행률: 도구는 보고만 하고, 루프가 이벤트로 바꾼다

날짜: 2026-10-29 · 상태: 채택

## 문제
회로 비서의 파라미터 스윕은 한 번의 도구 호출 안에서 점 7개든 50개든 돈다. 바깥(화면·잡 큐)에서는 시작과 끝만 보여서, 맡겨 둔 사람은 "지금 몇 번째 점인지" 를 알 수 없었다. 큐 보드(ADR-019 의 맡긴 작업 탭)에 진행 막대를 그리려면 도구 안의 진행 상황이 밖으로 나와야 한다.

## 결정
1. **도구는 `report(done, total, label)` 만 부른다.** `harness/tools/progress.py`. 누가 받는지 모르고, 수신자가 없으면 아무 일도 하지 않는다. 그래서 CLI·MCP·테스트에서 같은 도구를 그냥 불러도 안전하다.
2. **수신자는 에이전트 루프가 건다.** 도구를 실행하는 동안 `progress_scope(cb)`(contextvar, 스레드별)로 수신자를 걸고, 보고를 `progress` 이벤트(`name, done, total, label`)로 바꾼다. 이벤트는 기존 통로(저장소·SSE·`/runs/{id}/events`)를 그대로 탄다. 새 엔드포인트가 없다.
3. **0.4초에 한 번만 저장하되 마지막 점은 반드시.** 점 50개짜리 스윕이 이벤트 50개를 만들지 않게 묶고, 100% 는 꼭 남겨 막대가 끝까지 찬다.
4. **화면은 세 군데서 같은 이벤트를 쓴다.** 작업지의 기다리는 줄(스트리밍으로 바로), 맡긴 작업 탭의 큐 보드(2초 폴링), 오른쪽 요약의 진행 중 항목.
5. **큐 보드.** 최근 작업 12개를 시간선 위에 막대로: 대기는 점선 빈 막대와 "n번째 대기", 실행 중은 채워지는 막대와 "4/7 · R1=2.15 kΩ", 끝난 것은 소요 시간만큼의 막대. 누르면 작업지로 연다.

## 결과
- 스윕 점마다 보고가 나가고(`sweep` 에 한 줄), 루프 테스트는 0.4초 안에 다섯 번 보고하면 첫 점과 마지막 점 둘만 남는 것을 확인한다.
- 다른 긴 도구(공정 팩의 그래프, 지식 베이스 색인)도 같은 한 줄이면 막대가 생긴다.

## 대안과 기각 이유
- **도구가 실행 폴더에 progress.json 을 쓰고 화면이 파일을 읽기.** 회로 팩에만 통하고, 어느 파일이 어느 작업인지 잇는 열쇠(서비스 run id)를 도구가 모른다.
- **도구 핸들러에 콜백 인자를 넘기기.** 도구 서명이 전부 바뀌고 MCP 노출과 어긋난다. contextvar 는 서명을 건드리지 않는다.
- **A2A 의 status 메시지로만 전달.** 상위 비서에게는 되지만 같은 서비스의 화면에는 아무 도움이 안 된다.

## 한계
- 진행률은 도구가 보고해야 생긴다. 모델이 생각하는 시간(LLM 호출)은 점이 없으니 막대가 멈춘 것처럼 보인다. 그 구간은 "확인한 내용을 정리하는 중" 문구로 메운다.
- 예상 남은 시간은 아직 없다. 실험 추적 그래프의 점당 평균 시간으로 낼 수 있다.
