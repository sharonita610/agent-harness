# ADR-025 요청 다양화: 다중 턴·업무 흐름·추세·틀린 전제·설계·표현 변형

날짜: 2026-10-30 · 상태: 채택

## 배경

평가 61문제(회사 16 + 문서 그래프 5 + 회로 20 + 라이브러리 4 + 공정 17 + 총괄 8)가 전부 "한 번 묻고 한 번 답하는" 조회·규정·변경·함정이었다. 실제 사용은 그렇지 않다. 앞 답을 받아 이어 묻고("그중 A 등급만"), 한 요청에 조회→규정→계산→변경이 들어 있고, 틀린 전제("등급 D", "주문 99999")나 범위 밖("부산 담당자가 서울 주문")을 묻고, 숫자 하나가 아니라 추세와 이유를 묻고, 같은 질문을 반말·영어·긴 배경과 함께 묻는다. 비서가 이런 요청에서 어떻게 되는지 숫자가 없었다.

## 결정

여섯 종류를 세 팩에 39문제로 더했다(`tasks_enterprise_more.yaml` 23, `tasks_spice_more.yaml` 10, `tasks_factory_more.yaml` 6). 러너는 세 가지를 새로 할 줄 안다.

| 종류 | id | 러너·채점 | 예 |
|---|---|---|---|
| 다중 턴 `multiturn` | mt | `turns:` 목록. 앞 턴의 질문·답을 history 로 넘긴다(서비스와 같은 방식, 도구 메시지는 안 넘김). 마지막 턴을 채점하되 도구·승인은 전 턴 합산 | "지연 몇 건?" → "그중 A 등급은?" |
| 업무 흐름 `workflow` | wf | `expect_approval_args`: 승인 요청의 **인자**까지 본다(계산한 비율이 메모에 들어갔는가) | "며칠 지연인지 보고 규정 비율을 계산해 메모에 남겨라" |
| 추세·설명 `trend` | tr | `answer_regex_all` + 핵심 숫자 + 판정자 비고 | "월별 지연율 추세와 가장 높은 달" |
| 틀린 전제·범위 `premise` | pr | `scope:` 로 태스크별 사용자 범위(레지스트리·프롬프트를 서비스의 `registry_for`·`system_prompt_for` 와 같게 구성). 기대는 "없다/범위 밖/되묻기" | 부산 범위 사용자의 "서울 지연 주문" |
| 설계·진단 `design` | ds | 스윕 뒤 선택, 고장 넷리스트 수리, 부품 치환 비교, 원인 후보 → 조치 티켓 | "fc 가 1 kHz 에 가장 가까운 R 골라줘" |
| 표현 변형 `variant` | va | 기존 문제와 같은 정답, 반말·오타·영어·긴 배경 | "지연중인 주문 몇개임?" |

`{변수}` 치환(`params_sql`)은 질문뿐 아니라 태스크 전체(턴, 기대 인자, truth_sql)에 적용한다. 리포트는 태스크 파일별로 묶는다(`summary.tasks_file`).

## 결과

| 묶음 | 첫 실행 | 수정 후 | 유형별(수정 후) |
|---|---|---|---|
| 회사 23 × 3 | 81% | 88% | 다중 턴 93 · 업무 흐름 67 · 추세 89 · 틀린 전제 100 · 표현 변형 87 |
| 회로 10 × 3 | 77% | 80% | 다중 턴 100 · 틀린 전제 83 · 설계 58 · 표현 변형 100 |
| 공정 6 × 3 | 94% | 100% | 추세·틀린 전제·진단 전부 100 |

첫 실행과 수정 사이에 바뀐 것은 채점기(오류로 끝난 도구 호출도 "썼다" 로, 판정자 기준에 허용 오차)와 프롬프트(`discount_rate` 단위, 지연 일수 공식), 기대 문구 몇 개다. 남은 실패는 전부 모델의 몫이고 각각 무엇인지 README 평가 절에 적었다. 가장 값진 발견은 표현 변형이다: 같은 규정 질문을 "할인 200만원 승인권자?" 로 줄이면 로컬 모델이 2/3 틀린다.

## 대안과 기각 이유

- **대화형 평가를 서비스 API 로 돌리기(세션·SSE).** 서비스까지 띄워야 하고 결과 저장이 둘로 갈린다. 러너가 history 를 서비스와 같은 규칙으로 만들면 같은 것을 재는 셈이라 러너 안에서 했다.
- **표현 변형을 자동 생성(번역·패러프레이즈 모델).** 변형의 품질을 또 검증해야 한다. 손으로 쓴 5개면 "표현 민감도" 숫자 하나를 내기엔 충분하다.
- **추세·설명 문제를 판정자만으로 채점.** 판정자는 관대하다(ADR-011). 핵심 숫자와 정규식을 규칙으로 먼저 걸고 판정자는 "이유가 맞는가" 만 본다.

## 한계

- 총괄 비서(supervisor)는 하위 서비스 셋이 떠 있어야 해서 이번 묶음에 넣지 않았다.
- 다중 턴은 history 에 도구 결과를 넘기지 않는다(서비스와 같다). "방금 그 실행의 파형" 처럼 run_id 가 필요한 둘째 턴은 비서가 앞 답에 적어 둔 값에 의존한다.
- 틀린 전제 문제의 기대 문구("없", "범위")는 느슨한 문자열이라 판정자 대조가 필요하다.
