# ADR-026 설비 상태와 시뮬레이터 상태: "지금 이 기계 어때" 를 도구 하나로

날짜: 2026-10-30 · 상태: 채택

## 배경

사용자 질문: "2번(회로)·3번(공정) 팩에서 공정이나 기계 상태 같은 것도 조회할 수 있나?" 공정 팩은 설비표·정비 이력·시간별 파라미터·조치 티켓·알림 규칙을 전부 가지고 있었지만 비서가 닿는 길은 `run_sql` 과 급증 분석의 곁가지뿐이었다. "4라인 주입 설비 지금 온도 정상이야?" 에 답하려면 소형 모델이 네 테이블을 조인하고 문서 PE-003 의 관리 범위를 따로 찾아 대조해야 했다. 회로 팩에는 기계 개념이 없어서 "시뮬레이터 괜찮아?" 에 답할 것이 없었다.

## 결정

**공정 팩**: `equipment_status(설비 1대, 구간)` 와 `list_equipment(라인)` 두 도구. 구간(기본 데이터 끝 기준 최근 24시간)의 파라미터 평균·최신값을 **PE-003 관리 범위**(코드의 `PARAM_RANGES`, 테스트가 문서 표와 대조)와 비교해 정상/높음/낮음, 마지막 정비와 경과일(PE-007 정기 점검 30일 초과 표시), 열린 조치 티켓, 알림 규칙, 구간 NG 율을 한 번에 돌려주고 `issues` 와 `verdict`(정상/주의)로 요약한다. 데이터 탭에 같은 계산의 **설비 현황판**(24대, 주의 먼저)과 "주의 설비" 타일. 심어 둔 이상 A(히터 교체 뒤 온도 +8℃)가 10-18 09~14시 구간에서 "temp_c 31.9℃, 범위 22~27 밖" 으로 그대로 보인다.

**회로 팩**: `engine_status()`. ngspice 설치·버전, 최근 24시간 실행·스윕·실패 수와 평균 소요 시간, 마지막 실행, 저장 회로 수, 실험 그래프 노드 수. 대기 중인 잡(큐)은 서비스가 관리하므로 도구는 "화면의 큐 보드에서 본다" 고 안내한다.

## 결과

- 도구 수: 공정 16 → 18, 회로 17 → 18. 시드 기준 정기 점검 주기(30일)를 넘긴 설비 10대(최장 3라인 화성 53일) — 설비 현황판이 처음으로 드러낸 사실이다.
- 평가 묶음 `tasks_factory_equipment.yaml` 5문항(상태·구간 이탈·정비 경과·라인 주의 목록·다중 턴 티켓): 첫 실행 60% → 채점 기준(승인 인자로 설비 확인, 기대 문구) 수정 후 100%(15/15). `tasks_spice_engine.yaml` 3문항: 100%(9/9). 로컬 gpt-oss-20b, n=3.

## 대안과 기각 이유

- **관리 범위를 문서에서 매번 파싱.** 문서 표의 형식이 바뀌면 판정이 조용히 깨진다. 코드 상수 + "문서와 같은지" 테스트가 더 안전하다.
- **실시간 설비 연동(OPC-UA·MQTT).** 가짜 공장이라 데이터 원천이 없다. 인터페이스는 시간별 로그 테이블이므로 실제 설비 로그를 같은 표로 적재하면 그대로 쓴다.
- **회로 팩의 큐를 도구로 노출.** 큐는 서비스 상태라 팩이 보면 계층이 섞인다. 실행 폴더 기준 수치로 충분하다.

## 한계

- 파라미터 판정은 구간 평균 기준이라 짧은 튐은 묻힌다(PE-003 도 "분 단위 이상은 원본 로그" 라고 적는다).
- 범위가 문서에 없는 파라미터(조립 속도, 화성 압력)는 "범위 미정의" 로만 나온다.
