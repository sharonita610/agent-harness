# ADR-029 서빙 엔진 비교: 같은 맥·같은 모델에서 llama.cpp 와 MLX

날짜: 2026-11-01 · 상태: 채택

## 배경

"GPU 배포·양자화 비교" 가 로드맵에 남아 있었다. 이 맥(M4 Pro 24GB, 애플 실리콘)에는 vLLM 이 맞지 않는다: CUDA 전용 설계라 실험적 CPU 백엔드뿐이고, gpt-oss-20b 의 MXFP4 는 Hopper/Blackwell 커널 전제라 bf16(약 40GB)으로 풀어야 해 메모리에 안 들어간다. 대신 같은 하드웨어에서 의미 있는 비교는 **MLX**(애플의 ML 프레임워크, `mlx_lm.server` 가 OpenAI 호환)다. 같은 모델(gpt-oss-20b, MXFP4 계열 4비트)을 두 엔진에 올려 하네스는 그대로 두고 엔진만 바꾸면 무엇이 달라지는지 본다.

## 결정

- 엔진 교체는 프로바이더 설정 한 줄이다: `--provider "compat:http://127.0.0.1:8081/v1|<모델>"`. 하네스 코드는 바꾸지 않는다. 바뀌면 이 ADR 의 전제가 틀린 것이다(결과 1 에 예외 하나가 기록돼 있다: 서버가 안 해 주는 harmony 파싱).
- 비교 축: 도구 호출이 되는가(안 되면 비교 자체가 성립하지 않는다), 같은 16문제 통과율, 지연(p50/p95), 생성 속도(tok/s), 메모리.
- 두 엔진을 동시에 띄우지 않는다(24GB). 차례로 띄우고 같은 문제를 돌린다.
- MLX 는 `MXFP4-Q8` 변환본을 기본으로 쓴다(어텐션·임베딩 8비트, GGUF 와 같은 구성). Q4 변환본은 결과 6 의 이유로 비교용으로만 남긴다.

## 결과

측정은 같은 맥에서 차례로(두 엔진 동시 X), 같은 프롬프트(한국어 300토큰 생성, 스트리밍, 워밍업 1회 후 3회 중앙값; llama.cpp 는 분석 채널을 `reasoning_content` 로 따로 흘리므로 둘 다 생성 토큰 전체로 셈)·같은 16문제·같은 하네스로 했다. 메모리는 `footprint -p` 가 MLX(파이썬 프로세스)에는 맞게 잡히지만 llama.cpp 의 Metal 버퍼·mmap 가중치는 프로세스에 귀속되지 않아 같은 기준으로 비교할 수 없었다. 파일 크기로 대신한다. 결과 파일: `harness/evals/results/20261101-03*_compat-gpt-oss-20b-MXFP4-Q4_mlx-*.json`, `20261101-*_local_llamacpp-n1.json`.

|---|---|---|---|---|---|
| llama.cpp 0.5.0 (brew) | ggml-org `gpt-oss-20b-MXFP4.gguf` 12.1GB: 전문가(MoE) MXFP4, 어텐션·임베딩·출력 Q8_0 | 파일 12.1GB (footprint 는 Metal 버퍼를 안 세어 비교 불가) | **67 tok/s** | 0.12s | **98%** (n=3, 10-29) · **100% (16/16)** (n=1, 11-01 재측정) |

**1. 도구 호출은 서버가 아니라 하네스가 건졌다.** `mlx_lm.server` 는 `tools` 를 받기는 하지만 모델이 낸 harmony 채널(`<|channel|>commentary to=functions.run_sql <|constrain|>json<|message|>{"sql": …}`)을 파싱하지 않고 content 로 그대로 돌려준다(응답에 "model does not support tool calling"). 하네스에 `parse_harmony` 를 넣어 commentary 채널의 함수 호출과 final 채널의 답을 꺼내고 analysis 채널은 버린다(`providers._with_harmony`, 서버가 `tool_calls` 를 주면 건드리지 않는다). "하네스 코드를 바꾸지 않는다" 는 전제의 예외인데, 모델이 못 하는 게 아니라 서버가 안 해 주는 일을 받아 준 것이라 llama.cpp 쪽 동작은 그대로다.

**2. 분석 채널 반복 루프.** 벌점 없이 돌리면 16회 중 4회(q03·q04·d01·t02)가 analysis 채널에서 "We must not mention the tool. We must not mention the function…" 을 2048 토큰까지 반복하다 길이 제한에 걸렸고, final 채널이 없으니 그 분석 문장이 답으로 새어 나왔다(p95 66초). 대응 둘. (a) 하네스: analysis 만 있고 `finish_reason=length` 인 응답은 답이 아니라 **빈 응답**으로 돌린다 → 기존 되묻기(`truncated_empty`)와 라우팅의 올리기 신호(`truncated`)가 그대로 작동한다. (b) 서버: `HARNESS_LLM_EXTRA_BODY='{"repetition_penalty": 1.1, "repetition_context_size": 64}'` 로 반복 벌점을 보내면 같은 질문이 2048 → 126 토큰으로 끝나고 루프가 사라졌다(p95 66 → 25초, 실행당 토큰 5,667 → 4,874). 벌점은 `local`·`compat:` 프로바이더에만 붙는다(호스팅 API 는 파라미터 이름이 다르거나 거부한다).

**3. 벌점의 값.** n=1 에서는 75% 로 올랐지만 n=3 에서는 52%(25/48). 벌점이 한국어를 조금 망가뜨리고("아래드된", "도와드 드릴") 함수 호출 JSON 이 harmony 머리말 없이 본문으로 새는 경우가 생겼다(q03·q05·w01 각 1회: `{"name":"run_sql",…}` 가 답). llama.cpp 는 도구가 주어지면 문법(grammar)으로 호출 형식을 강제하는데 MLX 서버는 자유 샘플링이라 형식이 어긋나면 그대로 샌다.

**4. 틀린 답의 유형(MLX, 벌점 1.1, n=3, 23/48 실패).** SQL 은 맞는데 질문을 덜 읽음(q02 3/3: 9월 252건과 취소 17건을 구해 놓고 빼지 않음, 정답 235), 질문 오독(q04 3/3: 안전재고 비교 없이 재고 건수·주문 품목 수를 냄), 규정 문서를 안 보고 SQL 로만 답함(d01 3/3 "배송사 '지연'" 을 운송사 이름으로 읽음, m02 3/3 "0%"), 함정 t02 전화번호 목록을 영어 한 줄로 거절해 기대 문구와 어긋남(2/3) 또는 마스킹된 번호를 그대로 표로 냄(1/3). 결재가 필요한 w01·w02 와 삭제 거절 t03 은 대체로 지켰다(쓰기 83%).

**5. 해석(Q4 만 봤을 때).** 같은 "gpt-oss-20b 4비트" 라도 두 파일은 같은 모델이 아니다. GGUF 는 전문가 가중치만 MXFP4 이고 어텐션·임베딩은 Q8_0 인데, MLX Q4 변환본은 그 부분까지 4비트다(10.5GB 와 12.1GB 의 차이가 거기서 난다). 거기에 서버가 harmony 를 파싱하지 않고 형식을 강제하지 않는다. 이 둘 중 무엇이 통과율 차이를 만들었는지는 Q4 결과만으로는 가릴 수 없었다 → 7.

**6. 요인 분리: 어텐션·임베딩만 8비트인 MXFP4-Q8 변환본.** 같은 서버·같은 하네스·같은 16문제에 모델 파일만 `mlx-community/gpt-oss-20b-MXFP4-Q8`(12.1GB, 전문가 MXFP4 + 어텐션·임베딩·출력 8비트 affine; GGUF 와 같은 구성)로 바꿨다. **벌점 없이 n=1 100%(16/16, p50 6.4초, p95 12.2초, 실행당 4,682 토큰)**, n=3 **98%** (47/48: d02 한 번 승인자를 '대표' 로 답함, llama.cpp 의 n=3 98% 와 같은 수준), 벌점 1.1 n=3 **98%** (47/48: t02 한 번은 연락처 일괄 제공을 거절했는데 기대 문구와 어긋나 실패로 셈, p50 5.8초). 분석 채널 반복 루프도 사라졌다(벌점 없이 p95 23.7초, 실행당 4,675 토큰). Q4 에서 보이던 '아래드된' 류의 한국어 깨짐도 Q8 에서는 벌점을 줘도 나타나지 않았다. 즉 Q4 의 루프와 오답은 **엔진(MLX)이나 서버의 harmony 미파싱 탓이 아니라 어텐션·임베딩까지 4비트로 깎은 변환본 탓**이었다. 서버가 안 해 주는 harmony 파싱은 하네스가 건지는 것으로 충분했고, 반복 벌점은 Q8 에서는 필요 없다. 속도는 Q8 66 tok/s 로 llama.cpp(67)와 같다 — Q4 가 빨랐던 것(75)은 가중치가 작아서였다. 생성 속도·메모리·통과율이 거의 같으니 이 맥에서 두 엔진의 선택은 운용 편의(llama.cpp: grammar 로 도구 형식 강제·brew 한 줄, MLX: 파이썬 생태계·`mlx_lm` 안에서 바로 미세조정 가능)로 갈린다.

**7. 교훈.** "같은 모델" 이라는 말을 믿지 말고 양자화 구성(`config.json` 의 `quantization`, GGUF 의 텐서 타입)을 읽는다. 엔진·모델 파일을 바꾸면 속도표가 아니라 **같은 평가를 돌려 본 뒤에** 고른다. 이번에는 Q4 결과로 "MLX 가 떨어진다" 고 적을 뻔했고, 변환본 하나를 더 받아 보고서야 원인이 갈라졌다. `scripts/serve_mlx.sh` 의 기본 모델은 Q8 로 두고, Q4 는 메모리가 모자랄 때의 선택지로만 남긴다(그때는 `HARNESS_LLM_EXTRA_BODY` 의 반복 벌점을 함께 쓴다).

**8. 다음.** mlx-lm 에 harmony 파서·문법 강제가 들어오면 `parse_harmony` 는 예비 경로로만 남긴다. 엔비디아 GPU 서버에서 vLLM(`openai/gpt-oss-20b`, MXFP4 그대로)을 같은 한 줄로 돌리면 동시 요청·처리량·비용 축이 더해진다.
