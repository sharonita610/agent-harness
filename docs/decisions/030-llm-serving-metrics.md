# ADR-030 서빙 부하 테스트: TTFT·ITL·처리량을 동시 요청 수별로 잰다

날짜: 2026-11-01 · 상태: 채택

## 배경

ADR-029 는 단일 요청만 봤다(디코드 tok/s, 첫 토큰). 실제 서비스는 여러 사용자가 동시에 묻는다. 그때 중요한 것은 한 요청의 속도가 아니라 "동시 N 개일 때 첫 글자가 언제 나오고(TTFT), 글자가 끊기지 않고(ITL), 서버 전체가 초당 몇 토큰을 내는가(처리량)" 이고, 용량 계획과 SLO 는 이 셋으로 세운다. vLLM·SGLang 운영에서 보는 지표가 바로 이것인데 이 맥에는 엔비디아 GPU 가 없다. 그래서 엔진은 llama.cpp·MLX 로 두고 **측정 방법론과 도구**를 레포에 남긴다. GPU 서버가 생기면 베이스 URL 만 바꿔 같은 표를 뽑는다.

## 결정

- 클라이언트 쪽 부하 생성기 하나로 잰다: `scripts/bench_llm.py`. 표준 라이브러리만 쓴다(urllib + 스레드 + SSE 파싱). 파일 하나를 GPU 서버에 복사해도 돌고, OpenAI 호환 `/v1/chat/completions` 스트리밍만 전제하므로 llama.cpp·MLX·vLLM·SGLang 에 같은 코드다.
- 지표 정의와 보는 이유:
  - **TTFT**(time to first token): 요청을 보낸 순간부터 내용이 있는 첫 델타까지. 사용자가 느끼는 "반응" 이고, 서버 큐 대기 + 프롬프트 처리(prefill)가 들어 있다. 동시 요청이 슬롯·배치 한도를 넘으면 가장 먼저 여기가 튄다.
  - **ITL**(inter-token latency, TPOT 라고도 부른다): 연이은 델타 사이 간격. p50 이 체감 타자 속도(1/ITL 이 요청당 디코드 tok/s), p95 가 끊김(다른 요청의 prefill 끼어듦, 스케줄링, 발열 조절). 평균은 끊김을 숨기므로 백분위로 본다.
  - **처리량**(throughput): 한 동시 수준에서 생성된 토큰 전체 / 벽시계 초. 서버의 용량이고 비용(토큰당 GPU 초)의 분모다. 동시 수를 올리면 요청당 디코드는 떨어지지만 처리량은 오르다가 어딘가에서 꺾인다. 그 지점이 그 서버의 적정 동시 수다.
  - **요청당 디코드 tok/s** = (토큰 수 - 1) / (마지막 델타 - 첫 델타). 첫 토큰 이후의 순수 디코드 속도로, ADR-029 의 단일 요청 수치와 이어 본다.
  - **p50/p95**: TTFT 는 요청별 값의 분포, ITL 은 모든 요청의 간격을 한데 모은 분포. SLO 는 "대부분의 사용자" 기준이고, 큐 대기는 요청의 절반에만 생길 수 있어서(아래 llama.cpp c=8) 중앙값으로는 보이지 않는다. 요청이 8개면 p95 는 사실상 최댓값이다. 분포를 말하려면 `--repeat` 로 표본을 늘린다.
- 토큰을 세는 법: 스트리밍 델타 하나 = 토큰 하나. `content` 와 `reasoning_content` 모두 센다(gpt-oss 는 분석 채널이 따로 온다). 서버의 `usage.completion_tokens` 는 교차 확인용으로만 저장한다. 엔진마다 다르게 세면 비교가 성립하지 않는다.
- 실험 설계: 한국어 질문 8개(회사·회로·공정 주제, 도구 없음), 300토큰, temperature 0. 요청마다 시스템 프롬프트에 꼬리표를 붙여 프롬프트 캐시가 TTFT 를 줄이지 못하게 한다(실제 트래픽은 매번 다른 질문이다). 동시 수 1·2·4·8 을 차례로, 수준마다 8요청(프롬프트 묶음 한 번), 워밍업 뒤 측정. 닫힌 루프(closed loop)다: 동시 c 개의 작업자가 각자 요청이 끝나야 다음을 보내므로 클라이언트 큐 대기는 TTFT 에 들어가지 않고 서버 큐 대기만 들어간다.
- 두 엔진을 동시에 띄우지 않는다(24GB). 결과 파일은 `harness/evals/results/bench/`, 문서의 숫자는 그 파일에서 옮긴다.
- 지표 계산은 순수 함수(`percentile`, `request_metrics`, `level_summary`)로 두고 가짜 타임스탬프로 테스트한다(`tests/test_bench_llm.py`).

## 결과

조건: M4 Pro 24GB. gpt-oss-20b. llama.cpp 는 ggml-org MXFP4 GGUF 를 `scripts/serve_llm.sh 32768` 로(0.5.0 b11146, 슬롯 4, kv_unified, `-fa on`, KV q8_0). MLX 는 mlx-community MXFP4-Q8 을 mlx-lm 0.32.2 `mlx_lm.server` 로(`MLX_PORT=8091`). 수준마다 8요청, 300토큰, 1 → 2 → 4 → 8 순서.

| 2 | 8 | 29.0 | 2326 | 80.1 | 43.4 | 0.57 / 0.59 | 22.4 / 23.8 | 7.2 / 7.3 | 0 |
| 4 | 8 | 27.0 | 2327 | 86.2 | 23.2 | 0.99 / 1.01 | 42.1 / 43.4 | 13.5 / 13.5 | 0 |

- c=1 → 4: 처리량 58 → 80 → 86 tok/s, 요청당 디코드 64 → 43 → 23. 4개를 한 배치로 디코드하면 전체는 1.5배 늘고 개별은 1/2.8 로 떨어진다. TTFT 는 0.47 → 0.99초(4개의 prefill 이 같이 돈다).
- c=8: 슬롯 4 를 넘는 4개는 큐에서 기다린다. TTFT 가 둘로 갈라진다: 4개는 0.99초, 나머지 4개는 18.47초(첫 물결이 끝나는 16.5초 + 자기 prefill). p50 9.73초는 그 둘의 중간값일 뿐 어느 요청의 경험도 아니다. p95(18.47)가 실제 대기자의 경험이다. 처리량은 70.7 로 c=4 보다 낮았고 ITL p95 가 75ms 로 벌어졌다.
- 순서 효과(`20261101-llamacpp-c8-first.json`): 같은 서버에서 c=8 을 먼저 돌리면 처리량 90.8, 요청당 24.4 tok/s, ITL p50/p95 40.0/41.4ms, TTFT p50/p95 7.35/13.75초로, 이어 돌린 c=4(87.9, 23.6, 41.6/43.6ms)와 같은 수준이다. 즉 첫 실행의 c=8 저하는 대기 연결 탓이 아니라 2분째 연속 부하(발열 조절로 추정)와 순서 탓이다. 사다리 한 번으로 "c=8 에서 꺾인다" 고 적을 뻔했다.

- **가설이 틀렸다.** `mlx_lm.server` 가 요청을 직렬화할 것으로 예상했고 그걸 보여 주려고 이 측정을 넣었는데, mlx-lm 0.32.2 는 `ThreadingHTTPServer` + `BatchGenerator` 로 연속 배치를 한다(`server.py` 의 `_generate` 가 들어온 요청을 돌고 있는 배치에 `insert_segments` 한다. 조건: draft 모델 없음, 캐시가 `merge` 지원, `seed` 없음, `kv_bits` 없음). c=8 에서 8개가 전부 0.70~1.02초에 첫 토큰을 받고 동시에 16 tok/s 로 디코드해 처리량 124.6 tok/s. 소스를 읽어 확인했고, 측정이 가설을 덮어썼다.
- c=1 은 콜드 스타트가 섞였다. 워밍업 1회(TTFT 5.28초, 29 tok/s) 뒤에도 앞 4요청은 28~34 tok/s(ITL p50 29~38ms), 뒤 3요청은 62~63 tok/s(ITL p50 15.6~16.1ms). MLX 는 가중치를 지연 로드해 처음 수십 초는 디스크에서 페이지를 끌어온다. 그래서 c=1 요약(44.2 tok/s, ITL p95 49ms)은 엔진 속도가 아니라 워밍업 부족이고, 덥혀진 뒤 단일 스트림 62~63 tok/s 가 ADR-029(66)와 맞는다. 스크립트에 `--warmup N` 을 넣었다.
- c=2·4 는 덥혀진 상태다: 처리량 88 → 116, 요청당 46.5 → 30.1 tok/s. 같은 동시 수에서 llama.cpp 보다 요청당 디코드가 높다(c=4: 30.1 vs 23.2).
- 재측정 실패: 덥혀진 뒤 사다리를 다시 돌리려는 사이 다른 세션이 같은 맥에 llama-server(gpt-oss, `-c 65536`)를 띄워 두 엔진이 동시에 올라갔고, MLX 가 `[METAL] Command buffer execution failed: Insufficient Memory` 로 생성 스레드가 죽어 모든 요청이 404 "generation thread died" 였다. 24GB 에서 두 엔진 동시 금지 규칙의 이유를 몸으로 확인했다. 그 서버는 이 세션 것이 아니라 끄지 않았고 재측정은 남겨 둔다. 또 c=4·8 구간(05:41:19~58)이 그 서버의 기동(05:41:23, 12GB 적재)과 겹쳤다. ITL p95 가 p50 의 1.1배 안이라 눈에 띄는 간섭은 없었지만 깨끗한 재측정이 필요하다.

## 측정하면서 배운 것 (방법론)

1. **순서를 바꿔 한 번 더.** 사다리 한 번은 발열·캐시·연속 부하에 묶인다. c=8 이 마지막이면 70.7, 처음이면 90.8 이었다.
2. **워밍업은 "속도가 안정될 때까지".** 1회가 아니라 N 회, 워밍업의 디코드 속도가 기대값(ADR-029 의 단일 요청 수치)에 왔는지 보고 시작한다. MLX 는 1회로 부족했다.
3. **p95 는 표본 8개면 최댓값이다.** 여기서는 큐 대기의 이분화를 보여 주는 데는 충분했지만, 분포를 말하려면 `--repeat 3` 이상.
4. **토큰 셈 기준을 고정한다.** 델타 283~300 vs usage 300: harmony 제어 토큰(채널 전환)은 텍스트로 안 흐른다. 처리량은 3% 보수적이고 두 엔진에 같은 기준이다.
5. **측정 중 다른 부하를 막는다.** 두 엔진 동시 금지, 시작 전 `ps aux | grep -E "llama-server|mlx_lm.server"` 로 다른 세션의 서버를 확인. 워밍업이 실패하면 스크립트가 바로 멈춘다(죽은 서버로 빈 결과 파일을 만들지 않는다).
6. **가설은 적되 결과로 덮어쓴다.** "MLX 는 직렬화" 는 틀렸고, "c=8 에서 llama.cpp 가 꺾인다" 는 순서 효과였다.

## GPU 서버(vLLM·SGLang)에서 같은 스크립트

```bash
uv run python scripts/bench_llm.py --base http://<gpu>:8000/v1 --model openai/gpt-oss-20b \
  --concurrency 1 4 16 64 128 --repeat 4 --warmup 4 --api-key "$VLLM_API_KEY" \
  --json harness/evals/results/bench/<날짜>-vllm-<gpu>.json
```

- vLLM: `vllm serve openai/gpt-oss-20b --reasoning-parser openai_gptoss` 로 띄우면 분석 채널이 `reasoning_content` 로 와서 llama.cpp 와 같은 셈이 된다. `stream_options.include_usage` 도 지원한다. SGLang: `python -m sglang.launch_server --model-path openai/gpt-oss-20b --port 30000` → `--base http://<gpu>:30000/v1`.
- 거기서 더해지는 축:
  - **연속 배치(continuous batching)와 PagedAttention**: 처리량 곡선이 수십~수백 동시 요청까지 계속 오른다. 꺾이는 지점은 KV 캐시 메모리(`--gpu-memory-utilization`, `--max-num-seqs`, `--max-num-batched-tokens`)가 정한다. 그 지점부터 TTFT 가 큐 대기로 튀고 선점(preemption)이 생긴다. 여기서도 "요청 절반만 느려지는" 이분화가 p95 에 먼저 보인다.
  - **청크 프리필(chunked prefill)**: 긴 프롬프트의 prefill 을 쪼개 디코드 사이에 끼우면 ITL p95 가 안정되는 대신 TTFT 가 조금 는다. 이 스크립트의 ITL p95 와 TTFT p95 로 그 트레이드오프가 보인다.
  - **접두 캐시(prefix caching)**: 이 스크립트는 꼬리표로 일부러 막는다. 같은 시스템 프롬프트를 쓰는 실제 트래픽에서는 TTFT 가 더 짧다. 캐시 효과를 보려면 꼬리표를 빼는 플래그를 추가해 두 번 돌린다.
  - **서버 쪽 지표**: vLLM `/metrics`(Prometheus: `vllm:time_to_first_token_seconds`, `vllm:time_per_output_token_seconds`, `vllm:num_requests_running`, `vllm:num_requests_waiting`, `vllm:gpu_cache_usage_perc`)를 Grafana 로 보면 이 클라이언트 측정과 맞춰 볼 수 있다. llama.cpp 도 `--metrics` 로 `/metrics` 를 연다. 클라이언트 측정은 부하 테스트용, 서버 지표는 상시 모니터링용으로 역할이 다르다.
  - **goodput**: "TTFT < 1초 그리고 ITL p95 < 50ms 를 만족한 요청의 비율" 처럼 SLO 기준으로 세는 것이 다음 지표다. 결과 JSON 에 요청별 TTFT·ITL 이 있어 후처리로 계산할 수 있다.
  - **공식 도구와 교차 검증**: `vllm bench serve`, SGLang `bench_serving.py` 가 같은 지표(TTFT, TPOT, ITL, throughput)를 낸다. 같은 조건에서 한 번 나란히 돌려 이 스크립트의 숫자가 맞는지 확인한 뒤 쓴다.
