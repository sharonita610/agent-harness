# ADR-031 RAG 평가 확장: 청크 크기·인용 정확도·융합 가중

날짜: 2026-11-01 · 상태: 채택

## 배경

문서 검색(RAG)은 ADR-008(하이브리드)·ADR-014(지식 베이스)에서 "검색이 맞는 절을 찾는가"(hit@1·hit@3·MRR)만 쟀다. 세 가지가 빠져 있었다. (1) 청크 크기는 `MAX_CHUNK_CHARS=1800` 하나로 고정돼 있어 그 값이 좋은지 모른다. (2) 답에 적힌 "출처: 문서 > 절" 이 실제로 검색된 절인지는 채점하지 않았다. 검색이 맞는 절을 찾아도 모델이 다른 절을 적거나 지어내면 사용자는 틀린 곳을 뒤진다. (3) RRF 융합의 상수 k 와 BM25·벡터 가중치는 60, 1:1 로 고정돼 있었다. 이 ADR 은 셋을 각각 옵션으로 열고 같은 평가로 재서 기본값을 정한다.

## 결정

- **청크 크기는 옵션이다.** `harness retrieval-eval --chunk-chars N`(마크다운 색인, 절이 N 자를 넘으면 문단 경계에서 나눔)과 `harness kb build --chunk-chars N --out …`(지식 베이스는 만들 때 정해지므로 파일을 따로 두고 `retrieval-eval --kb` 로 비교). 환경변수 `HARNESS_CHUNK_CHARS` 는 둘의 기본값. **기본은 1800 그대로** 둔다(아래 결과 1·2).
- **인용 정확도를 채점한다.** 루프가 검색 도구 결과의 절 목록을 `tool_calls[*].result_sources` 에 남기고(`retrieval/citation.extract_sources`: `{"hits": […]}`·목록·`{"source": …}` 꼴만, SQL 결과는 아님), 태스크에 `expect_citation: true` 가 있으면 러너가 `cite_matches_retrieval` 검사를 더한다. 판정: 답의 인용("출처: 문서 > 절", 꼬리표 없는 "(문서 > 절)", "문서" 가 생략된 쉼표 나열)을 전부 모아, **하나 이상 있고 전부** 이번 실행에서 검색된 절과 맞아야 참. 맞는다는 것은 공백·괄호·따옴표를 뺀 소문자 문자열로 문서명 부분 일치 + 절 제목 부분 일치(매뉴얼은 절 번호 일치도 인정). 검색 결과가 없으면 어떤 인용도 거짓(검색 없이 적은 출처는 지어낸 것). 통과율 계산은 그대로(다른 검사와 같이 `pass` 에 들어간다)이고, 요약에 `citation_accuracy`(검사한 실행 중 맞은 비율)와 `citation_checked` 를 따로 적는다. 실행 기록에는 `citations.cited`·`citations.retrieved` 를 남겨 틀린 이유(출처를 안 적었나, 다른 절을 적었나)를 나중에 볼 수 있게 한다.
- **융합 가중은 옵션이다.** `search(query, k, mode, rrf_k, bm25_weight, vector_weight)` 와 `retrieval-eval --rrf-k/--bm25-weight/--vector-weight`. 두 색인(`DocIndex`·`KnowledgeBase`)이 같은 `rrf_fuse` 를 쓴다. **기본은 k=60, 1:1 그대로** 둔다(결과 3).
- 기존 결과 파일은 다시 채점하지 않는다. 새 검사는 `expect_citation` 이 있는 태스크에만 붙고, 전 실행에는 `result_sources` 가 없어 재채점하면 전부 거짓이 된다.

## 결과

임베딩은 로컬 embeddinggemma-300m(llama.cpp, 포트 8092: 8082 는 다른 프로세스가 쓰고 있었다). 질문은 회사 18개(`retrieval.yaml`)·회로 32개(`retrieval_spice.yaml`). 결과 파일: `harness/evals/results/retrieval_20261101-05*_{c150,c900,c1800,c3600,k10,k200,w2-1,w1-2}.json`(회사), `retrieval_20261101-05*_spice-kb_{orig,c900,c1800,c3600,k10,k200,w2-1,w1-2}.json`(회로). 회사 문서 1문항 = 5.6%p, 매뉴얼 1문항 = 3.1%p 임을 염두에 두고 읽는다.

**1. 청크 크기, 회사 규정 문서 10개.** 절이 가장 길어야 293자라 900·1800·3600 은 전부 같은 42청크다(표의 세 줄이 같다). 요청받은 세 값으로는 아무것도 바뀌지 않는다는 것이 결과라서, 절보다 작은 150자를 한 줄 더 넣어 "절을 더 쪼개면" 을 봤다.

| 청크 상한 | 청크 수 | BM25 hit@1 / hit@3 / MRR | 벡터 | 하이브리드 |
|---|---|---|---|---|
| 150 (절 8개가 쪼개짐) | 50 | 89% / 94% / 0.92 | 94% / 100% / 0.97 | 94% / 100% / 0.97 |
| 900 | 42 | 89% / 94% / 0.91 | **100% / 100% / 1.00** | 94% / 100% / 0.97 |
| 1800 (기본) | 42 | 89% / 94% / 0.91 | **100% / 100% / 1.00** | 94% / 100% / 0.97 |
| 3600 | 42 | 89% / 94% / 0.91 | **100% / 100% / 1.00** | 94% / 100% / 0.97 |

절 아래로 쪼개면 벡터가 1문항("주소를 잘못 적어서 늦어진 건 누구 책임" 이 주문 상태 정의 대신 배송 지연 보상 규정)을 잃는다. 짧은 규정 문서는 **절 하나가 청크 하나** 가 맞고, 청크 상한은 절이 상한보다 길 때만 의미가 있다.

**2. 청크 크기, ngspice 매뉴얼 765쪽 + 요약 문서 7개.** 지식 베이스를 세 개 만들고(`kb build --chunk-chars`, 각각 `kb embed`) 같은 32문항을 돌렸다. 1800 은 10-28 에 만든 원래 지식 베이스(1,174청크, 요약 문서가 그때는 6개)와 수치가 같다.

| 청크 상한 | 청크 수 | BM25 hit@1 / hit@3 / MRR | 벡터 | 하이브리드 |
|---|---|---|---|---|
| 900 | 1,783 | **88% / 97% / 0.92** | **75% / 94% / 0.84** | **84% / 97% / 0.90** |
| 1800 (기본) | 1,178 | 84% / 100% / 0.92 | 69% / 91% / 0.79 | 81% / 94% / 0.87 |
| 3600 | 925 | 84% / 100% / 0.92 | 66% / 88% / 0.75 | 81% / 97% / 0.89 |

벡터는 청크가 작을수록 좋다(66 → 69 → 75%): 1800자 절 하나에는 `.AC` 문법·옵션·예제가 섞여 있어 벡터 하나가 뭉개지는데, 900 에서는 `.AC dec oct lin …`·`.TRAN TSTEP …`·`capacitor … initial condition`·`diode model parameters` 가 벡터 1위로 올라왔다. BM25 는 1800 과 3600 이 같고 900 에서 1문항(MOSFET instance line) 더 맞혔다. 반대로 900 에서 `inductor element syntax` 는 세 모드 전부 놓쳤다(3.3.10 절이 둘로 갈려 "syntax" 를 담은 조각이 밀렸다). 차이는 1~2문항이고 32문항에서 1문항은 3.1%p 라 "900 이 조금 낫다" 까지만 말할 수 있다. 기본값을 바꾸려면 검색 도구가 청크 앞 600자만 보여 주는 `search_manual` 과 회로 팩 20문항 평가를 900 청크로 다시 돌려 봐야 하고, 호스팅 임베딩(text-embedding-3-small)은 1800 지식 베이스에만 들어 있어 이번 세션(외부 호출 없음)에서는 비교할 수 없었다. 그래서 **기본은 1800 을 유지**하고 900 을 다음 후보로 적어 둔다.

**3. 융합 가중(청크 1800, 하이브리드만 바뀐다).**

| 설정 | 회사 하이브리드 hit@1 / hit@3 / MRR | 매뉴얼 하이브리드 |
|---|---|---|
| k=60, 1:1 (기본) | 94% / 100% / 0.97 | 81% / 94% / 0.87 |
| k=10 | 94% / 100% / 0.97 | 81% / 94% / 0.87 |
| k=200 | 94% / 100% / 0.97 | 81% / 94% / 0.87 |
| BM25 2 : 벡터 1 | 94% / 100% / 0.97 | **84% / 97% / 0.90** |
| BM25 1 : 벡터 2 | **100% / 100% / 1.00** | 75% / 91% / 0.82 |

k 는 10~200 어디서도 순위를 바꾸지 못했다(후보 풀이 12개뿐이라 두 목록에 같이 든 절이 어차피 위로 가고, k 는 그 안의 간격만 바꾼다). 가중치는 방향이 있다: **그 말뭉치에서 더 강한 신호 쪽으로 기울이면 하이브리드가 그 신호의 단독 성적까지 올라가고, 반대로 기울이면 떨어진다.** 회사 문서는 벡터(100%)가 BM25(89%)보다 강해서 벡터 2 가 하이브리드를 100% 로 끌어올렸고(ADR-008 에서 놓쳤던 "거래처 등급은 어떻게 정해져" 복구), 매뉴얼은 BM25(84%)가 벡터(69%)보다 강해서 BM25 2 가 84% 로 올리고 벡터 2 는 75% 로 떨어뜨렸다. 모든 말뭉치에 맞는 가중치는 없으므로 **기본은 1:1 로 두고**, 팩별로 `retrieval-eval` 을 돌려 본 뒤에 그 팩의 `search` 호출에 가중치를 주는 쪽을 택한다(한 문항 차이는 노이즈 범위라 이번에는 바꾸지 않는다).

**4. 인용 정확도(로컬 gpt-oss-20b, llama.cpp, BM25 검색, 프롬프트 v1, n=3).** 회사 `tasks.yaml` 16문제(출처 검사 5문제: d01~d03·m01·m02)와 `tasks_enterprise_more.yaml` 23문제(출처 검사 7문제: mt04·wf01~wf03·tr02·va04·va05)를 돌렸다. 결과 파일 `20261101-065937_local_cite-n3.json`, `20261101-070514_local_more-cite-n3.json`.

| 묶음 | 통과율 | 출처 검사를 뺀 통과율 | 출처 정확도 | p50 / p95 |
|---|---|---|---|---|
| tasks.yaml 16문제 × 3 | 93.8% (45/48) | 95.8% (46/48) | **86.7%** (13/15) | 6.1s / 15.3s |
| tasks_enterprise_more 23문제 × 3 | 89.9% (62/69) | 92.8% (64/69) | **81.0%** (17/21) | 7.7s / 21.2s |
| 합계(출처 검사 36회) | | | **83.3%** (30/36) | |

틀린 6건의 유형. (a) 답은 맞는데 출처를 아예 안 적음 2건(m01, wf01). (b) 검색 없이 답함 1건(d01: 주문의 `discount_rate` 0.15 를 보고 "보상 비율은 15%" 라고 답했는데, 기존 검사 `answer_contains_any: ["5%"]` 는 "15%" 안의 "5%" 를 보고 통과시켰다. `tools_any` 와 출처 검사가 잡았다). (c) 형식 밖의 인용 1건(wf03: '월말 마감 절차 문서(문서번호 FIN-007) "마감 전 점검 항목"에 따르면' 처럼 "문서 > 절" 도 "출처:" 도 없이 본문에 녹였다. 절 자체는 검색된 것이 맞아 파서의 한계이자 형식 이탈이다). (d) 출처에 문서가 아닌 것을 섞음 1건(tr02: "주문 상태 정의 > 지연 사유 코드" 옆에 "테이블 조회 결과" 를 출처로 적음). (e) 문서명만 적고 절이 없음 1건(tr02: 비율 계산도 틀린 실행). **검색되지 않은 절을 지어내 적은 경우는 0건**이다: 모델이 "문서 > 절" 꼴로 적은 인용은 전부 그 실행의 검색 결과에 있었다. 이 모델·이 프롬프트에서 출처 문제는 환각이 아니라 **누락과 형식**이다. 인용 형식 분포(36회): "출처:" 꼬리표 25, 괄호·따옴표 안 "(문서 > 절)" 만 7, 없음 4.

비교: 같은 묶음의 직전 실행은 tasks.yaml 100%(10-28 n=3, 11-01 n=1), 추가 묶음 88.4%(10-30 n=3). 이번 통과율이 조금 낮은 것은 출처 검사가 더해진 몫(2.1%p, 2.9%p)과 모델 변동(w02 승인 요청 누락 1, wf02 건수 2, va04 승인자 1)이다. 기존 결과 파일은 다시 채점하지 않았다(재채점하면 `result_sources` 가 없어 출처 검사가 전부 거짓이 된다).

**5. 다음.** 누락 2건·형식 1건은 프롬프트 v2("끝에 '출처: 문서명 > 절' 을 적습니다")로 줄어들 가능성이 있어 같은 검사로 v1·v2 를 비교한다. 매뉴얼 쪽(`search_manual`·`read_manual`)도 `result_sources` 를 남기므로 회로 팩 문서 질문(`tasks_spice.yaml` 의 doc 유형)에 `expect_citation` 을 켜 보면 영어 절 제목·절 번호 인용의 정확도가 나온다. 청크 900 은 회로 팩 20문항을 그 청크로 다시 돌려 본 뒤 기본값 교체를 결정한다.

## 교훈

- 청크 상한은 "절이 그보다 길 때" 만 일하는 값이다. 말뭉치의 절 길이 분포(회사 문서 최대 293자, 매뉴얼 절 평균 1,500자 안팎)를 먼저 보고 실험 범위를 정한다. 이번에 900/1800/3600 이 회사 문서에서 같은 결과를 낸 것은 실험이 틀린 게 아니라 그 사실을 숫자로 적어 둔 것이다.
- 융합 가중은 두 신호의 단독 성적을 먼저 재야 방향이 보인다. k 를 돌리는 실험은 후보 풀이 작을 때 아무것도 안 바꾼다.
- "출처를 적었다" 와 "출처가 맞다" 는 다른 검사다. 후자는 그 실행의 검색 결과를 같이 저장해야만 가능하고, 그래서 루프가 `result_sources` 를 남긴다.
