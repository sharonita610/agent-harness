# ADR-032 총괄 비서 병렬 위임: 서로 의존하지 않는 하위 질의는 한 번에 보낸다

날짜: 2026-11-01 · 상태: 채택

## 배경

총괄 비서(`harness/packs/supervisor/`)는 분야별 비서 셋(회사 8786 · 회로 8788 · 공정 8789)에 A2A `message/send`(blocking)로 질문을 위임하고 답을 합친다(ADR-017). 지금까지 위임은 **순차**였다. 도구 `delegate` 가 한 번에 비서 하나만 부르고, 모델은 스텝마다 그 도구를 하나씩 호출했다. 복합 질문("RC 차단 주파수 + 2라인 권취 NG 급증 원인", r04)은 `list_agents` → `delegate(회로)` → `delegate(공정)` → 답, 4스텝 44초(n=3 평균)였고, 그중 두 위임은 서로 아무 관계가 없는데 뒤 비서가 앞 비서의 답을 기다렸다. 하위 비서 하나가 보통 6~18초를 쓰니 독립 질의가 둘이면 그만큼 그대로 더해진다.

A2A 쪽은 이미 태스크마다 스레드로 돌아(ADR-017 추가, 결재 대기가 다음 태스크를 막지 않게) 하위 비서 셋이 동시에 일할 수 있었다. 병목은 상위의 루프와 도구였다.

## 결정

**(a) 위임 도구에 묶음 입력을 더한다: `delegate_many(items=[(비서, 질문), ...])`.** 도구 안에서 비서별 스레드(`ThreadPoolExecutor`)로 동시에 보내고 결과를 items 순서로 돌려준다. 에이전트 루프는 손대지 않는다.

- **의존 관계는 비서 단위로 보존한다.** 같은 비서(url)로 가는 항목은 한 A2A 세션(contextId)이고 앞 답이 다음 질의의 입력일 수 있으므로 적은 순서대로 보낸다. 비서가 다르면 동시. 비서를 가로지르는 의존(회사 비서의 답을 회로 비서에 넣어야 하는 경우)은 모델이 기존 `delegate` 를 차례로 쓴다. 프롬프트 원칙 2 에 "독립 질의는 한 번에 보내라" 를 넣고, `delegate` 는 "앞 답이 다음 질문의 입력일 때" 로 역할을 좁혔다.
- **결재 대기(`input-required`)는 항목별로 그대로.** 각 항목은 `delegate` 한 건과 같은 모양(`agent`, `task_id`, `state`, `answer`, 결재 대기면 `waiting_for` + 안내)이고, 묶음 머리말 `delegated: [{agent, state}, ...]` 와 `note` 에 "결재 대기 항목: 회사. 그 항목은 '결재 대기' 로 보고하고 나머지 답은 그대로 전달한다" 가 붙는다. 상위 비서가 결재를 기다리거나 `check_task` 로 폴링하지 않는 ADR-017 의 원칙은 그대로다.
- **부분 실패는 부분 결과로.** 비서를 못 찾은 항목, A2A 오류, HTTP 실패는 그 항목만 `state=error` + `error` 문구로 남고 나머지 항목은 답을 돌려준다. 예외를 묶음 전체로 올리지 않는다. 비서 선택(`_pick`, 카드 조회)은 스레드를 만들기 전에 호출 스레드에서 끝내 카드 캐시 경쟁을 피한다.
- **출처 유지.** 항목마다 `agent`(비서 id)가 그대로 있어 모델이 "출처: 어느 비서" 를 쓰고, 화면은 항목마다 인용 카드 하나를 그린다(`ResultCard.tsx`). 평가의 `expect_calls` 는 `name: [delegate, delegate_many]` 로 어느 도구를 썼든 위임 대상(agent id)을 확인한다. 묶음 결과의 머리말을 짧게 둔 이유가 이것이다: 도구 로그 미리보기(300자) 안에 모든 비서 id 가 들어가야 채점이 된다.
- 묶음은 1~6개, 각 항목 대기 상한은 `wait_s`(기본 180초). `contexts`(비서별 세션 id)는 잠금으로 보호한다.

### (b) 를 고르지 않은 이유
"루프가 한 스텝에서 낸 여러 도구 호출을 병렬로 실행(병렬 안전 표시가 있는 도구만)" 도 가능했다. 더 일반적이지만 두 가지가 걸렸다. 첫째, 속도가 나려면 **모델이 한 응답에 도구 호출을 둘 이상 내야** 하는데, 지금 로컬 모델(gpt-oss-20b, llama.cpp 의 문법 강제)은 스텝마다 하나씩 냈다(r04 4스텝, va01 3스텝이 그 흔적). 묶음 인자 하나는 소형 모델도 안정적으로 만든다. 둘째, 루프의 이벤트 순서·도구 로그·진행률 contextvar·결재 핸들러를 스레드 안전하게 바꿔야 하고, 네 팩의 도구 전부에 "병렬 안전" 을 표시해야 한다. 위임은 총괄 비서 한 팩의 문제이고 I/O 대기라서 도구 안에서 푸는 쪽이 작고 검증이 쉽다. 루프 수준 병렬은 다른 팩에서 같은 요구가 나올 때 (b) 로 다시 본다.

### 실패 분석 (병렬 묶음)
- **r05 보상 비율 2/3 실패는 하위 비서 층의 일이고 위임 방식과 무관하다.** 총괄 비서는 세 번 모두 `delegate` 로 질문을 글자 그대로 회사 비서에 보냈다(10-29 와 같은 호출). 회사 비서가 규정 문서(`search_docs`, 5%)를 보지 않고 `orders.discount_rate` 평균(15%·1.8%)을 SQL 로 냈다. 같은 비서에 따로 물어보면(새 세션 2회, "지연 몇 건" 뒤 같은 세션 2회) 4/4 `search_docs` 로 5% 를 답한다. 평가에서는 A2A 세션 하나에 "지연 몇 건"(SQL) 이 세 번 쌓인 뒤 이 질문이 들어가 SQL 쪽으로 끌린 것으로 보인다(10-29 에도 같은 순서였으나 그때는 3/3 문서를 봤다. 그 사이 회사 팩의 프롬프트·도구가 바뀌었다). 15% 답 하나는 "5%" 가 부분 문자열로 들어가 통과로 셌다. 같은 날 순차 대조에서 r05 가 어떻게 나오는지가 이 해석의 검증이다.
- **va01 1/3 실패는 채점 형식이다.** 답 "약 1 590 Hz(1 587 Hz 시뮬레이션, 1 591 Hz 공식값)" 는 맞지만 정규식 `1[.,]?5[89]` 가 천 단위 공백(회로 비서가 Hz 로 적은 것을 총괄이 그대로 인용)을 받지 않는다. 숫자를 바꾸지 말라는 원칙을 지킨 결과라 채점을 사후에 고치지 않고 그대로 둔다.
- **pr01 1/3 실패는 10-30 과 같은 비율(67%)** 이고 모양만 다르다: 공정 비서는 "1~4라인만 있다" 고 바르게 되물었는데 총괄 비서가 최종 답으로 질문 문장을 그대로 냈다(모델의 되뇌기). `delegate` 한 번짜리 문제다.

### 해석
- **스텝은 줄었다**: 복합 문제 r04 4.0 → 2.3(A)·2.0(C), va01 3.7~4.0 → 2.7(모델이 묶음 호출 하나로 두 비서를 불렀다, 모든 병렬 실행 9/9·6/6). 묶음 전체에서도 평균 스텝 2.67 → 2.08·2.04, 3.5 → 2.67·2.83.
- **벽시계 지연은 줄었지만 두 배는 아니다**: r04 는 같은 날 순차 대조 35.7초 → 병렬 33.6초(A)·27.8초(C), 즉 −6%·−22%(10-29 의 37.8초 기준 −11%·−26%). va01 은 깨끗한 순차 대조 27.4초 → 22.9초(A)·20.7초(B), −16%·−24%. 위임(도구) 시간은 r04 20.1 → 16.7·17.3초, va01 11.5 → 11.1·10.9초다. 두 하위 비서를 동시에 보냈는데 왜 max(6초, 13초) ≈ 13초가 아니라 16~17초인가. **모델 서버가 하나**라서다. 회로·공정 비서가 같은 GPU 에서 동시에 디코드하면 슬롯당 속도가 떨어져 둘의 합산 계산량은 그대로이고, 겹쳐서 아끼는 것은 ngspice 실행·SQL·HTTP·A2A 폴링(0.3초) 같은 비계산 대기뿐이다. 총괄 비서 자신의 모델 시간은 표본에 따라 15.6초(순차 대조) → 16.8초(A)·10.5초(C)로 들쭉날쭉하다. 호출 수는 4 → 2 로 줄지만 묶음 호출의 인자(질문 둘)와 합친 답이 길어 호출당 토큰이 늘고, 모델이 `list_agents` 를 먼저 부르는지(A 1회, C 0회)와 추론 길이에 따라 크게 흔들린다. 벽시계에서 가장 큰 변동 요인은 위임 방식이 아니라 이 추론 길이다.
- 즉 **이 구조의 병렬 위임은 "순차 오케스트레이션" 이 아니라 "공유 GPU 처리량" 에 묶여 있다.** 하위 비서가 각자 모델 서버를 갖거나(GPU 서버·호스팅 API) 하위 비서의 시간이 I/O(외부 API·DB·시뮬레이터)에 치우칠 때 비서 수에 비례해 줄어든다. 단위 테스트의 가짜 비서(답 0.4초, 모델 없음)에서는 두 질의가 0.8초 → 0.4초로 정확히 절반이 된다.


## 검증
- 단위 테스트 `tests/test_supervisor_parallel.py`: 가짜 하위 비서 둘(한 명당 0.4초)로 (1) 동시 위임이 순차(0.8초+)보다 빠른 것(0.6초 미만, 두 요청의 시작 시각이 겹침), (2) 한쪽이 `input-required` 일 때 그 항목은 결재 대기·다른 항목은 답으로 합쳐지고 `note` 가 두 가지를 모두 말하는 것, (3) 같은 비서의 두 항목은 순서대로 contextId 를 이어 보내고 터지는 비서·없는 비서 항목은 `error` 로 남되 나머지는 답을 받는 것, (4) 루프 한 스텝의 묶음 호출이 미리보기에 두 비서 id 를 모두 남겨 `expect_calls` 가 인정하는 것과 기존 `delegate` 만 쓴 결과도 새 yaml 로 그대로 통과하는 것.
- 기존 A2A 테스트(`tests/test_a2a.py`)와 스모크(`scripts/smoke.py`, 총괄 비서 도구 5개)는 그대로.

## 한계
- 동시성은 하위 비서 수(3)에 묶인다. 같은 비서로 가는 독립 질의는 세션을 하나로 두는 설계라 여전히 순차다(세션을 항목마다 새로 열면 동시에 보낼 수 있지만 다중 턴 이어 묻기가 끊긴다).
- 모델 서버가 하나라 하위 비서 둘이 동시에 생성하면 슬롯을 나눠 쓴다. 벽시계 시간은 줄지만 두 배까지는 아니다(측정 참조).
- 묶음 도구는 모델이 "독립" 을 맞게 판단해야 한다. 틀리게 묶으면(앞 답이 필요한 질문을 같이 보내면) 뒤 비서가 조건 없는 질문을 받는다. 프롬프트가 이를 막고, 평가의 다중 턴 문제(mt01)가 이어 묻기를 지키는지 본다.
