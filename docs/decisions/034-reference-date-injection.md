# ADR-034 데이터 기준일 주입: "오늘" 은 시드 상수가 아니라 스냅샷 시각이다

날짜: 2026-11-02 · 상태: 채택

## 배경

비서가 "오늘" 로 삼는 날짜가 각 팩 시드의 상수(`seed.REFERENCE_DATE = 2026-10-27`)였다. 세 곳이 그 상수에 묶여 있었다.

1. **프롬프트**: "오늘 날짜: 2026-10-27 … '지난달' 은 2026-09 입니다". 지난달 계산이 `f"{year}-{month - 1:02d}"` 라 1월이면 "2026-00" 이 된다.
2. **도구**: 미출고 지연 주문의 지연 일수(오늘까지), 거래처의 최근 12개월, 공정 설비의 정비 경과 일수, 데이터 탭의 "최근 7일·6개월·14일", 공정 도구의 기본 조회 구간(`PERIOD_START/END` 상수 "2026-10-14 ~ 2026-10-28").
3. **평가 문제**: "지난달(2026년 9월)" 과 `LIKE '2026-09%'`, `julianday('2026-10-27')` 가 yaml 에 박혀 있었다(회사 팩 14곳).

합성 데이터에서는 이것이 맞는 선택이다: 날짜를 고정해야 "지난달" 같은 상대 표현이 평가에서 흔들리지 않는다(ADR-003). 그러나 실데이터는 스냅샷을 찍은 시각이 기준이고 그 값은 매일 바뀐다. README 의 HR 절은 "데이터 기준 시각을 프롬프트로 알린다(`REFERENCE_DATE` 자리)" 라고 적어 두었지만 자리만 있고 주입 경로가 없었다(ADR-033 "남은 것").

## 결정

**기준일은 한 곳(`harness/refdate.py`)에서 정하고, 프롬프트·도구·평가가 전부 그 값을 본다.** 우선순위:

1. 환경변수 `HARNESS_REFERENCE_DATE` = `YYYY-MM-DD` | `today`
2. DB 의 `_meta` 표(`key='reference_date'`). 스냅샷 스크립트가 `write_reference_date(db, 날짜)` 로 적는다
3. 팩 기본(시드 날짜)

잘못된 값(`어제`, 날짜 아닌 `_meta`)은 조용히 넘기지 않고 `ValueError` 다. 출처(`env` / `env:today` / `db` / `default`)를 함께 돌려주고 `/health` 의 `pack.reference_date_source` 로 보인다.

**팩 인터페이스**: `Pack.reference_date`(해석된 날짜, 날짜 개념이 없는 팩은 None), `reference_date_source`, `system_prompts_for(ref)`(다른 기준일로 프롬프트를 다시 렌더). 회사·공정 팩은 모듈을 읽을 때 `resolve_reference_date(시드 날짜, DEFAULT_DB)` 로 한 번 정해 `SYSTEM_PROMPTS` 를 렌더하고(서비스·CLI·MCP 가 쓴다), `build_tools(reference_date=)` 로 도구에 같은 값을 넘긴다. 공정 팩의 "데이터 기간" 은 오늘과 다른 개념이라 DB 의 검사 기록 범위에서 읽는다(`data_period`: `MIN/MAX(hour_start)`, DB 가 없으면 시드 상수).

**평가 러너**: 평가 DB 의 `_meta` > 팩 기본으로 기준일을 정하고(`resolve_reference_date(pk.reference_date, pack_db)`), 프롬프트는 `system_prompts_for(ref)`, 도구는 `build_tools(reference_date=ref)`, 태스크는 `date_vars(ref)` 로 채운다. 변수는 `{ref_date}`, `{last_month}`(YYYY-MM), `{last_month_label}`(YYYY년 M월), `{last_month_start}`, `{this_month_start}`, `{this_month_short}`(M월), `{month-N_label}`, `{ref_date-N}` / `_md` / `_ko`(N일 전) 등이고 `params_sql` 안에서도 쓴다. **채우지 못한 `{변수}` 가 질문·turns·truth_sql 에 남으면 러너가 거절한다**: 틀린 SQL 을 조용히 돌려 엉뚱한 정답을 만드는 것이 가장 나쁜 실패다. 결과 파일의 `summary.reference_date` 에 그날의 기준일이 남는다.

**태스크**: `tasks.yaml`·`tasks_enterprise_more.yaml` 의 날짜 14곳을 변수로 바꿨다. 공정 팩 태스크의 "10월 18일" 은 그대로 둔다: 그 날짜는 "오늘" 이 아니라 시드가 심어 둔 이상(2라인 권취 급증)의 위치, 즉 쌍둥이 데이터의 속성이다. 실데이터 공정 평가는 그 데이터에서 다시 만들 문제고(README "기존 DB 를 붙일 때"), 기준일만 옮겨서는 성립하지 않는다.

## 왜 이렇게

- **DB 안의 `_meta` 를 두 번째 출처로**: 스냅샷 파일 하나가 데이터와 기준 시각을 함께 들고 다닌다. 파일을 옮기거나 평가를 다른 날 돌려도 기준이 데이터와 어긋나지 않는다. 환경변수는 운영자가 덮어쓰는 길이고, `today` 는 라이브 복제본처럼 "데이터가 오늘 것" 일 때만 맞다.
- **시드 DB 에는 `_meta` 를 넣지 않았다**: 시드 해시(`sha256_16`, CI 가 대조)가 바뀌고, 합성 시드의 기준은 코드 상수로 충분하다.
- **모듈 읽을 때 한 번 정한다**: 서비스는 뜰 때의 기준일로 하루를 간다. 스냅샷을 교체하면 서비스를 다시 띄우는 운영 모델(README HR 절의 `hr.db.tmp` → 교체)과 맞다. 평가는 평가 DB 마다 다시 정한다.
- **변수 이름을 사람 말로**: `{last_month_label}` 이 "2026년 9월" 로 렌더되어 질문이 예전 글자와 똑같다. 지금까지의 평가 결과와 비교 가능성을 잃지 않는 것이 조건이었다.

## 결과

- 시드 기준일로 렌더한 **프롬프트 3개(회사 v1·v2, 공정)와 태스크 67개(질문·turns·정답·정규식)가 변경 전과 글자 단위로 같다**(변경 전 스냅샷과 대조). 그래서 기존 평가 결과와 그대로 비교된다.
- 테스트 7개 추가(`tests/test_refdate.py`), 전체 253개 통과, ruff 통과.
- 기준일을 옮긴 평가(로컬 gpt-oss-20b, `HARNESS_REFERENCE_DATE=2026-11-02 harness eval --limit 6 --tag refdate-1102`): 질문이 "지난달(2026년 10월)" 로, 정답 SQL 이 10월로 같이 움직였고 `summary.reference_date = 2026-11-02` 가 남았다. **5/6** 통과: q02 지난달 주문 219건·m01 재고 부족 지연 16건을 10월 기준으로 맞혔다. 실패 q03 은 모델이 취소 주문을 빼지 않고 합계를 내서 1위 거래처가 달라진 것(10월에는 취소 1건이 순위를 바꾼다. 9월 데이터에선 안 드러났던 모델의 기본값 문제이고 기준일 주입과는 무관). 결과: [`20261102-014755_local_refdate-1102.json`](../../harness/evals/results/20261102-014755_local_refdate-1102.json).
- 커밋: 코드 `c1158b7`, 문서 커밋.

## 한계

- 서비스는 뜰 때 기준일을 정한다. 운영 중 `_meta` 가 바뀌어도 다시 띄우기 전까지는 모른다(스냅샷 교체 뒤 재기동이 운영 모델).
- 평가 변수는 "N일 전·N달 전" 꼴(60일·12달)만 있다. "다음 분기" 같은 표현은 필요할 때 더한다.
- 공정 팩 태스크는 여전히 시드의 이상 날짜를 가리킨다(의도, 위 "태스크").
- 사용자 화면은 기준일을 아직 보여 주지 않는다(`/health` 에만). 실데이터면 머리말에 "데이터 기준: 2026-11-02 06:00" 을 띄우는 것이 다음이다.
