# ADR-035 열 민감도 등급표와 뷰 단계 마스킹: 출력 열 이름이 아니라 데이터 층에서 가린다

날짜: 2026-11-02 · 상태: 채택

## 배경

회사 팩의 개인정보 마스킹은 `MASK_COLUMNS = {"phone"}` 하나와 파이썬 함수 `_mask_phone` 이었다. 조회 결과를 돌려주기 직전에 **출력 열 이름이 phone 인 열**만 가렸다. README 는 "전화번호 컬럼은 어떤 경로로 조회해도 `033-****-6001` 로 나간다" 고 적었다.

실데이터 전제로 다시 보니(ADR-033 "남은 것") 두 문제가 있었다.

1. **우회된다.** 실측(2026-11-02, 시드 DB):

   | SQL | 결과 |
   |---|---|
   | `SELECT name, phone FROM customers` | `033-****-6001` (가려짐) |
   | `SELECT phone AS tel FROM customers` | `033-819-6001` **원문** |
   | `SELECT substr(phone, 1, 12) AS p FROM customers` | **원문** |
   | `SELECT group_concat(phone) AS all_phones FROM customers` | 거래처 50곳 번호 **전부 원문** |

   모델이 악의가 없어도 별칭을 쓰는 일은 흔하다. 가드는 읽기 전용 연결과 authorizer 로 "쓰기" 를 데이터 층에서 막는데, "가림" 만은 응답을 만드는 파이썬 층에 있었다.
2. **열 하나가 코드에 박혀 있다.** 실 스키마의 `contact`, `manager_tel`, `email`, `resident_no`, `address` 는 이름이 달라서 안 가려진다. README 의 HR 절은 "민감도 등급표를 먼저 적는다" 고 했지만 그 표를 적을 자리가 코드에 없었다.

## 결정

**민감도 등급표를 팩이 들고, 뷰 단계에서 적용한다.**

- `harness/packs/enterprise/sensitivity.py`: `SENSITIVITY = {"customers": {"phone": "phone"}}`. 등급은 `phone`(국번 + `-****-` + 뒤 4자리), `email`(`***@도메인`), `full`(값 전체 `***`), `drop`(열 자체를 뷰에서 뺀다, 조회하면 "no such column"). 적지 않은 열은 그대로. 이름(`manager`, `author`)은 가리지 않는다(ADR-028 의 판단 그대로).
- `harness/tools/sql.py` `build_views(conn, policy, where, hide_unlisted_except)`: 테이블마다 **같은 이름의 임시 뷰** 하나에 열 마스킹(등급표), 행 필터(사용자 범위), 기본 거부(ADR-033)를 함께 넣는다. SQLite 는 temp 스키마를 먼저 찾으므로 모델의 어떤 SELECT 도(별칭·함수·조인·`group_concat`·CTE·서브쿼리) 뷰를 거친다. 마스킹은 SQL 식(`MASKS`)이라 값이 모델에게 가기 전에 DB 안에서 끝난다.
- 회사 팩 `scope.apply_scope(conn, scope | None, policy)`: 범위가 없는 사용자에게도 마스킹 뷰를 씌운다. 뷰가 하나라도 있으면 `main.customers` 같은 스키마 명시를 가드가 막는다(전에는 범위 사용자에게만).
- `describe_table` 은 열마다 `sensitivity` 라벨("마스킹(전화: 국번과 뒤 4자리만)", "비노출(뷰에서 빠져 조회 불가)")을 붙인다. 모델이 비노출 열을 조회하거나 마스킹된 값을 데이터 오류로 여기지 않게.
- **등급표의 오타는 즉시 실패다.** 표의 테이블·열이 DB 에 없거나 등급이 모르는 값이면 연결을 만들지 않는다. "안 가려진 채 조용히 통과" 가 가장 나쁜 실패이기 때문이다.
- 출력 열 이름 기준 파이썬 마스킹은 2차 층으로 남긴다. 겹쳐도 같은 값이 나오게 했다(이미 `****` 면 그대로, 국번은 `-` 앞).
- 공정 팩은 등급표가 비어 있다(가짜 공장에 개인정보 열이 없다). 자리(`SENSITIVITY`, `masked_connection`)만 만들어 실데이터(작업자 이름·연락처·사번)를 붙일 때 표만 채우면 되게 했다. 데이터 탭도 같은 연결을 쓴다.

## 왜 뷰인가

- **범위와 같은 장치다.** 행 범위(ADR-010)가 이미 임시 뷰였다. 열 마스킹을 같은 뷰에 넣으면 두 장치가 서로를 덮어쓰지 않고(둘 다 `customers` 라는 뷰를 만들려 하면 하나가 진다), 코드 경로가 하나다.
- **파서보다 단순하다.** SQL 을 파싱해 phone 열 참조를 찾는 방법도 있지만 별칭·함수·CTE 를 다 따라가야 하고, 하나 놓치면 그대로 샌다. 뷰는 놓칠 곳이 없다.
- **대가**: 마스킹된 값으로는 조인·정렬·비교가 안 된다(`WHERE phone = '033-819-6001'` 은 빈 결과). 업무상 전화번호로 거래처를 찾는 질문이 있으면 `get_customer(name=…)` 같은 전용 도구가 맡는다. 등급표에 `drop` 을 쓰면 그 열은 집계도 못 한다. 이것이 "열 단위 통제 ↔ 뷰에 없는 질문은 못 답함" 의 교환이다(README 트레이드오프 표).

## 한계

- 등급표는 열 단위다. "같은 열이지만 어떤 역할에게는 원문" (급여는 HR 담당만) 은 역할별 등급표(scope 와 함께 사용자 파일에서 고르기)가 필요하다. 지금은 모두에게 같은 표다.
- 마스킹 식은 SQLite 함수(`substr`, `instr`, `replace`)로 썼다. 다른 DB 방언에 붙일 때는 어댑터와 함께 옮긴다(README HR 절의 ①).
- 자유 텍스트 열(메모 본문) 안에 적힌 번호는 뷰가 모른다. 그것은 기록 가리기(ADR-028·033)가 저장본에서 잡고, 답변에 나가는 것은 프롬프트 규칙과 함정 평가(t02)가 본다.
