# LangGraph 비교 실험

같은 도구(우리 `ToolRegistry`), 같은 로컬 모델(gpt-oss-20b), 같은 평가 문제와 채점기로 **LangGraph 의 표준 ReAct 그래프**(`agent → tools_condition → ToolNode → agent`)를 돌렸다. 목적은 두 가지다. 프레임워크를 쓸 줄 아는지, 그리고 직접 쓴 루프에 프레임워크가 주지 않는 무엇이 들어 있는지를 같은 조건에서 보는 것.

```bash
scripts/serve_llm.sh   # 로컬 모델
uv run --with "langgraph>=0.2" --with "langchain-openai>=0.2" python docs/experiments/langgraph/run.py --pack enterprise --limit 6
uv run --with "langgraph>=0.2" --with "langchain-openai>=0.2" python docs/experiments/langgraph/run.py --pack spice --limit 8
```
의존성은 프로젝트에 넣지 않고 실행 때만 받는다(`uv run --with`). 결과: `results-enterprise.md`, `results-spice.md`.

## 결과 (n=1, 2026-10-29)
| 팩 | 문제 | LangGraph ReAct | 우리 루프(n=3, README 표) |
|---|---|---|---|
| 회사 데이터 | q01~q05, m01 | 6/6, 평균 2.5스텝 6.0s | 같은 문제 전부 통과(98~100%) |
| 회로 시뮬레이션 | s01~s08 | 8/8, 평균 3.1스텝 17.7s | s06·s08 이 67~88% 로 흔들림 |

같은 도구와 모델이면 **기본 루프의 정답률은 프레임워크와 직접 구현이 다르지 않다.** 회로 팩에서 LangGraph 가 s06·s08 을 한 번에 맞힌 건 표본이 1회라 우연일 수 있고, ToolNode 가 한 스텝의 도구 호출을 병렬로 전부 실행하는 차이(우리는 스텝당 4개 상한·중복 제거)도 있다. 단정하지 않는다.

## 어디서 갈리나
프레임워크가 주는 것: 그래프 상태와 체크포인트(대화 재개), 노드 단위 스트리밍, `interrupt` 로 사람 개입, 표준 도구 변환. 우리 루프에 **추가로** 들어 있고 LangGraph 그래프에는 없는 것:

| 우리 루프 | LangGraph 기본 그래프에서는 |
|---|---|
| 권한 3등급과 사람 결재(브로커, 시간 초과, 감사 기록) | `interrupt` + 체크포인터로 직접 짜야 한다. 이 실험에선 write 도구를 "승인 없음" 응답으로 대체 |
| 소형 모델 실패 모드 보정(글로 쓴 도구 되묻기, 중복 호출 제거·상한, 빈 출력 재시도, 잘린 호출 복구) | 없음. 모델이 같은 호출을 25번 만들면 25번 실행된다 |
| 컨텍스트 예산(긴 결과 절단, 오래된 결과 압축) | 메시지 상태가 그대로 자란다. 직접 트리밍 노드를 넣어야 한다 |
| 이벤트 → 스팬 트레이스, 사람 대기 시간 분리, OTLP | LangSmith 연동이 쉽다(유료/외부). 로컬 OTLP 는 직접 |
| 평가 러너(과정 검사·허용오차·판정자·사람 채점) | 별도 도구 |

결론: 루프 자체는 어느 쪽으로 짜도 되고, 프레임워크를 쓰면 체크포인트와 스트리밍을 공짜로 얻는다. 이 프로젝트의 가치는 루프가 아니라 그 위에 올린 운영 층(결재·실패 모드·예산·관측·평가)이고, 그 층은 어느 루프 위에도 올릴 수 있게 도구·정책·채점기를 루프와 분리해 두었다(이 실험이 그 분리를 그대로 썼다).
